# wb-sync

Сервис синхронизации магазинов Wildberries: забирает FBS-заказы из Marketplace API, ведёт каталог товаров,
склады и остатки, выгружает изменившиеся остатки в WB и проверяет, что WB их действительно применил.
Читает карточки товаров из Content API.

Стек: PHP 8.4, Laravel 12, MySQL 8.4, Redis, Horizon, Pest.

## Возможности

- **Магазины** — несколько магазинов WB, у каждого свой API-токен (хранится в БД зашифрованным).
- **Заказы** — инкрементальная загрузка `GET /api/v3/orders` по курсору `next`: каждые 5 минут
  планировщик ставит в очередь задачу `SyncShopOrders` на каждый активный магазин. Заказы пишутся через
  upsert по `(shop_id, wb_order_id)`, курсор сохраняется после каждой страницы, поэтому прерванная
  синхронизация продолжается с места остановки. `orders_synced_at` ставится только после полного прохода
  (до пустой страницы) и равен моменту его начала: все заказы до этого времени точно загружены.
- **Лимиты WB** — клиент сам ограничивает частоту запросов на токен: Marketplace API —
  `WB_REQUESTS_PER_SECOND`, Content API — 1 запрос в секунду, у каждого API свой счётчик. При ответе 429
  задача возвращается в очередь через `X-Ratelimit-Retry` секунд.
- **Очередь** — общие настройки задач магазина вынесены в трейт `ShopJob`: задача уникальна на магазин
  (`ShouldBeUnique`) и не выполняется параллельно (`WithoutOverlapping`), до 20 попыток, не больше 3 настоящих
  ошибок, паузы 30 с / 2 мин / 5 мин. Там же общий цикл по складам: бюджет времени, возврат в очередь при
  429, ошибка одного склада не останавливает остальные и выбрасывается в конце. Команды `app:sync-orders`,
  `app:push-stocks`, `app:verify-stocks` ставят задачу на каждый активный магазин через общий трейт
  `DispatchesShopJobs`. Выгрузка и сверка остатков одного магазина делят одну блокировку:
  занятая выгрузка ждёт минуту, занятая сверка пропускается — следующий запуск её догонит. Планировщик
  запускается `onOneServer`.
- **Бюджет времени** — задача работает не дольше 240 секунд и завершается сама, а остаток работы забирает
  следующий запуск по расписанию. Порядок таймаутов проверяется тестом: бюджет 240 < таймаут задачи 300 <
  таймаут супервизора Horizon 330 < `retry_after` очереди 360.
- **Каталог и остатки** — товары, размеры (`chrt_id`), баркоды, склады и остатки по складам. В `synced_amount`
  хранится то, что последним ушло в WB, поэтому выгружаются только изменившиеся позиции.
- **Выгрузка остатков** — каждые 5 минут задача `PushShopStocks` отправляет изменившиеся остатки в
  `PUT /api/v3/stocks/{warehouseId}` пачками до 1000 позиций, начиная со склада, который дольше всех не
  выгружался. Если остаток изменился во время запроса, расхождение `amount ≠ synced_amount` отправит его снова.
  Результат пачки записывается одним `UPDATE … SET synced_amount = CASE id WHEN … END`, а не запросом на
  каждое количество (то же для пометок об ошибках и результатов сверки).
  Если исход запроса неизвестен (таймаут, обрыв, 5xx, воркер убит посреди запроса), позиции снова ставятся
  на отправку: повторить своё значение безопасно, а потерять его — нет.
- **История выгрузок** — каждый запрос пишется в `stock_uploads` / `stock_upload_items` до отправки.
  Статусы: `in_progress` → `sent` или `failed` (с кодом и текстом ответа WB); после сверки `sent` становится
  `verified`, `mismatch` или `unverified`; запрос, оставшийся `in_progress` больше часа, — `interrupted`.
  Записи старше `WB_HISTORY_DAYS` дней (по умолчанию 30) вместе с позициями удаляет `model:prune` каждый
  день в 04:00.
- **Ошибки WB при выгрузке** разделены на три группы:
  - временная блокировка (406, `StoreIsProcessing`, `UploadDataLimit`) — склад пропускается до следующего
    запуска, позиции не помечаются;
  - проблема товара (остальные 409: `NotFound`, `SubjectRestriction`, `TnvedRequired`, …) — помечаются только
    виноватые позиции (`failed_amount`, `failed_code`) с кодом своей группы ответа: по `chrtId` из ответа WB,
    а если их нет — делением пачки пополам (не больше 32 запросов за запуск, неразобранное ждёт следующего
    запуска без пометки). Помеченная позиция повторяется, когда изменится количество или пройдут сутки;
  - ошибка запроса (400, 404) — задача падает и видна в Horizon.
- **Сверка «204, но не обновилось»** — WB отвечает 204 даже на запрос с неверными полями, не меняя данные.
  Раз в 10 минут (на 3-й минуте, между выгрузками) задача `VerifyShopStocks` читает остатки обратно
  (`POST /api/v3/stocks/{warehouseId}`, до 1000 размеров на запрос) и сравнивает с отправленным:
  - проверяются выгрузки последнего часа, отправленные не раньше чем 2 минуты назад и до последней полной
    синхронизации заказов; не проверенные за час получают `unverified`;
  - не судятся позиции, которые уже отправлены заново, и позиции, по которым после выгрузки был заказ с того
    же склада: продажа законно уменьшает остаток в WB;
  - фактическое значение WB сохраняется в `wb_amount`; размер, которого нет в ответе WB, считается нулём;
  - расхождение увеличивает видимый счётчик `not_applied_count`, а повторно отправляется только если в WB
    **больше**, чем мы отправили. Если в WB меньше, это может быть продажа, и повторная отправка вернула бы
    проданный товар — поэтому сверка никогда не увеличивает остаток в WB и никогда не блокирует выгрузку.
- **Карточки товаров** — клиент читает `POST /content/v2/get/cards/list` (Content API, отдельный хост
  `WB_CONTENT_URL`) по курсору `updatedAt` + `nmID`, до 100 карточек за запрос, пока страница не окажется
  неполной. Карточки из корзины WB в этот список не попадают. Загрузка карточек в каталог и проверка размеров
  до отправки остатков — следующий шаг.
- **Эмулятор WB** — в окружениях `local` и `testing` доступен фейковый WB API (`/fake-wb/...`):
  заказы с курсором, приём и чтение остатков, список карточек с курсором и корзиной, rate limit с заголовками
  `X-Ratelimit-*`, а также режимы ошибок для ручной проверки: отказ 409 по размеру, блокировка склада 406,
  «204 без сохранения».

## Запуск в Docker

```bash
cp .env.example .env
docker compose up -d --build
docker compose exec app composer install
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate
```

Сервисы `compose.yaml`:

| Сервис      | Назначение                                     |
|-------------|------------------------------------------------|
| `app`       | `php artisan serve`, http://localhost:8030      |
| `horizon`   | обработчик очередей (Redis)                     |
| `scheduler` | `php artisan schedule:work`                     |
| `mysql`     | MySQL 8.4, с хоста — `127.0.0.1:3312`           |
| `redis`     | очереди, кеш, rate limiter                      |

Тестовая база `wb_sync_testing` создаётся при первом старте MySQL (`docker/mysql/init.sql`).
Локальные переопределения (порты, сеть) — в `compose.override.yaml`, он не коммитится.

## Настройки `.env`

| Переменная                | По умолчанию                              | Описание                                          |
|---------------------------|-------------------------------------------|---------------------------------------------------|
| `WB_MARKETPLACE_URL`      | `https://marketplace-api.wildberries.ru`  | базовый URL Marketplace API                       |
| `WB_CONTENT_URL`          | `https://content-api.wildberries.ru`      | базовый URL Content API (карточки товаров)        |
| `WB_REQUESTS_PER_SECOND`  | `5`                                       | сколько запросов в секунду делать с одного токена |
| `FAKE_WB_RATE_LIMIT`      | `0`                                       | лимит запросов в секунду у эмулятора, `0` — без лимита |
| `REDIS_QUEUE_RETRY_AFTER` | `360`                                     | когда очередь считает задачу потерянной; больше таймаута задач |
| `WB_HISTORY_DAYS`         | `30`                                      | сколько дней хранить историю выгрузок остатков    |

## Команды

```bash
# добавить магазин (токен спрашивается скрыто)
php artisan app:create-shop "Мой магазин"

# поставить в очередь синхронизацию заказов, выгрузку остатков и сверку с WB
# (то же делает планировщик: заказы и выгрузка каждые 5 минут, сверка каждые 10 минут на 3-й минуте)
php artisan app:sync-orders
php artisan app:push-stocks
php artisan app:verify-stocks

# демо-каталог для магазина: склады 507 и 508, товары, размеры S/M/L, баркоды, случайные остатки
php artisan app:demo-catalog <shop_id> --products=3

# изменить остаток размера на складе
php artisan app:set-stock <chrt_id> <wb_warehouse_id> <amount>

# снять пометки об ошибках WB и счётчики расхождений у остатков магазина
php artisan app:reset-stock-errors <shop_id>
```

Команды эмулятора:

```bash
php artisan app:fake-wb-add-orders <token> 100                          # добавить N заказов
php artisan app:fake-wb-stocks <token> <wb_warehouse_id>                # что лежит в «WB»
php artisan app:fake-wb-reject-chrt <token> <chrt_id> TnvedRequired     # 409 по размеру (--hide-ids, --off)
php artisan app:fake-wb-block-warehouse <token> <wb_warehouse_id>       # 406 по складу (--off)
php artisan app:fake-wb-drop-chrt <token> <chrt_id>                     # 204, но не сохранять (--off)
php artisan app:fake-wb-add-cards <token> 5                             # добавить N карточек по 3 размера
php artisan app:fake-wb-trash-card <token> <nm_id>                      # убрать карточку в корзину (--off)
```

## Синхронизация с эмулятором

1. В `.env` указать `WB_MARKETPLACE_URL` и `WB_CONTENT_URL` равными `http://app:8000/fake-wb` — по этому
   адресу контейнер `horizon` достучится до `app` (при `network_mode: host` — `http://127.0.0.1:8030/fake-wb`).
2. Создать магазин с любым токеном: `php artisan app:create-shop Test`.
3. Нагенерировать заказы под этот токен: `php artisan app:fake-wb-add-orders <token> 2500`.
4. Запустить `php artisan app:sync-orders` и смотреть задачи в Horizon: http://localhost:8030/horizon.

Чтобы проверить обработку 429, задать `FAKE_WB_RATE_LIMIT` меньше `WB_REQUESTS_PER_SECOND`.

Остатки с эмулятором (`<shop_id>` и `<token>` — магазин и его токен):

1. `php artisan app:demo-catalog <shop_id>`, затем `php artisan app:push-stocks` —
   `php artisan app:fake-wb-stocks <token> 507` покажет выгруженное, в `stock_uploads` — записи `sent`.
2. Ошибка товара: `app:fake-wb-reject-chrt <token> <chrt_id> --hide-ids`, изменить остатки через
   `app:set-stock` и снова `app:push-stocks` — в `stock_uploads` видна цепочка деления пачки, у размера
   заполнены `failed_amount` и `failed_code`, остальные позиции выгружены.
3. Блокировка склада: `app:fake-wb-block-warehouse <token> 508` — склад 508 пропускается с записью
   `failed 406`, задача при этом не падает.
4. «204, но не обновилось»: `app:fake-wb-drop-chrt <token> <chrt_id>`, уменьшить остаток через
   `app:set-stock`, выполнить `app:push-stocks`, затем `app:sync-orders`, через 2 минуты `app:verify-stocks` —
   у выгрузки статус `mismatch` («отправлено 3, в WB 12»), остаток снова стоит на отправку, счётчик
   `not_applied_count` вырос.

## Структура

```
app/Console/Commands/              artisan-команды
app/Console/Commands/Concerns/     постановка задачи на каждый активный магазин
app/Jobs/Concerns/ShopJob          общие настройки задач магазина и цикл по складам
app/Jobs/SyncShopOrders            синхронизация заказов одного магазина
app/Jobs/PushShopStocks            выгрузка изменившихся остатков магазина
app/Jobs/VerifyShopStocks          сверка выгруженных остатков с WB
app/Services/Wildberries/          HTTP-клиент WB и DTO ответов
app/Exceptions/Wildberries/        лимит 429 и разбор отказов WB по остаткам
app/Support/ValuesById             CASE-выражение для обновления строк одним запросом
app/Services/FakeWildberries/, app/Http/Controllers/FakeWildberries/   эмулятор WB
routes/console.php                 расписание
routes/fake-wb.php                 маршруты эмулятора
```
